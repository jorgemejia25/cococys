Saber — Paradigma POO

¿Qué es la POO?

Paradigma que modela el mundo real con objetos: cada entidad combina datos y comportamiento en una unidad coherente.

▹Clase = molde o plantilla (ej. plano de una casa).
▹Objeto = instancia concreta creada a partir de ese molde.
Clase Ticket
Define qué datos y acciones puede tener cualquier ticket.
Objeto ticket #42
Instancia real: "Impresora no funciona", prioridad 3, estado Abierto.

Atributos = datos que describe el objeto. Métodos = comportamiento: acciones que el objeto puede realizar.

Saber — POO03 / 06

Encapsulamiento

Ocultar los datos internos con campos private y exponerlos mediante propiedades public. Protege la integridad del objeto.

+private — solo la clase accede al campo
⇔public property — acceso controlado desde fuera
Ticket.cs
class Ticket { private string _estado = "Abierto"; public string Estado { get => _estado; set => _estado = string.IsNullOrWhiteSpace(value) ? _estado : value; } }

Herencia

SoporteTicket hereda de Ticket: reutiliza atributos y métodos de la clase base, y agrega comportamiento propio.

:Sintaxis: class SoporteTicket : Ticket
basebase(...) invoca el constructor de la clase padre

class SoporteTicket : Ticket { public string TecnicoAsignado { get; set; } public SoporteTicket(int id, string titulo) : base() { Id = id; Titulo = titulo; Estado = "Abierto"; } }

Saber — POO05 / 06

Polimorfismo

Con virtual y override, el mismo método produce distinto comportamiento según el tipo real del objeto.

virtualEn la clase base: método que puede redefinirse
overrideEn la subclase: implementación específica
Ticket.cs
// En Ticket (base) public virtual string Resumen() => $"Ticket #{Id}: {Titulo}"; // En SoporteTicket (derivada) public override string Resumen() => $"[SOPORTE] #{Id} → {TecnicoAsignado}";
abs
Saber — POO06 / 06

Abstracción

Una clase abstracta define el contrato sin implementación completa. Obliga a las subclases a concretar los métodos abstractos.

abstractTicketBase — no se instancia directamente
!Métodos abstractos sin cuerpo; las hijas deben implementarlos
TicketBase.cs
abstract class TicketBase { public int Id { get; set; } public abstract string Resumen(); public abstract void Cerrar(); } // SoporteTicket : TicketBase implementa Resumen() y Cerrar()

Saber — HerramientaCONTROL DE VERSIONES

Git y control de versiones

¿Por qué versionar? Cada commit es una fotografía del código en un momento dado. Permite colaborar, revertir errores y documentar el avance del proyecto.

terminal — bash
$ git init # iniciar repo $ git add . # preparar cambios $ git commit -m "feat: clase Ticket" $ git log --oneline # ver historia
config
Saber — HerramientaSETUP

Configuración inicial de Git

Antes del primer commit, identifica quién eres en el historial. El archivo .gitignore excluye carpetas que no deben versionarse.

@user.name y user.email — autor de cada commit
!.gitignore — bin/, obj/, .vs/, node_modules/
terminal — bash
$ git config --global user.name "Tu Nombre" $ git config --global user.email "tu@email.com" # .gitignore bin/ obj/ .vs/ *.user

Saber — WorkflowRAMAS

Git Flow

Modelo de ramas estructuradas: main (producción estable), develop (integración) y feature (trabajo aislado por funcionalidad).

main
Código estable y desplegable. Solo entra vía merge revisado.
develop
Rama de integración donde convergen las features antes de release.
feature/*
Rama temporal por tarea: feature/ticket-poo, feature/git-setup.
merge
Saber — WorkflowCOMANDOS

Branching y Merging

Crear ramas permite trabajar en paralelo sin afectar main. El merge integra los cambios de una rama en otra.

1git branch feature/ticket — crear rama
2git checkout feature/ticket — cambiar a ella
3git merge feature/ticket — integrar en develop/main
terminal — bash
# flujo típico $ git checkout -b feature/soporte-ticket # ... editar código, commit ... $ git checkout develop $ git merge feature/soporte-ticket # develop ahora incluye los cambios

Saber — WorkflowSEMVER

Tags y versionamiento semántico

SemVer: MAJOR.MINOR.PATCH — v1.0.0 (inicial), v1.1.0 (nueva funcionalidad), v1.1.1 (corrección).

vgit tag v1.0.0 — marcar un punto en el historial
-agit tag -a v1.0.0 -m "..." — tag anotado con mensaje
terminal — bash
$ git tag -a v0.1.0 -m "Primera versión POO" $ git tag # listar tags $ git show v0.1.0 # ver detalle # v1.0.0 → release estable # v1.1.0 → nueva feature (SoporteTicket)
